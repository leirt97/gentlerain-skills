# 单缺陷修复 SOP

## 1. 接单

确认以下信息，形成简短输入卡：

- `编号/标题`：使用上游来源或 Craft 问题跟踪已经解析的唯一编号和简短名称；本 SOP 消费编号，不在修复阶段重新分配编号。
- `范围`：产品端、仓库和明确排除项。
- `现状/期望`：具体当前现象与验收结果；期望可由充分证据推导。
- `证据`：截图、日志、复现步骤、关联任务和环境信息；引用其他任务前先读取原任务。
- `来源`：Craft 来源须记录项目文档、合集和条目 ID，开始前读取 [Craft 来源回写](references/craft-feedback.md)，将原条目纳入交付。

关键业务行为、数据契约或用户可见结果仍有歧义时，一次只问一个问题。非简单修改先读取仓库约束，检查分支和工作树，确认最小文件范围及计划。

## 2. 复现、诊断与修复

1. 建立最小可失败复现，修改前运行并确认因本缺陷失败，能区分修复前后行为。优先复用测试；无法自动化时记录精确手工步骤和限制。
2. 沿实际调用链、组件归属或生命周期验证根因；截图、批注和发生先后仅作线索，必要时检查历史代码。
3. 证据指向外部系统、环境配置或旧部署状态时，停止推测性代码修复并报告。
4. 在最窄责任边界修复本缺陷，保留正常路径和仓库基线。

## 3. L1/L2 验证

先执行最快的相关 L1 检查：

- 定向回归与必要的邻近行为测试。
- 类型检查和定向 Lint。
- 相关平台或生产构建。
- `git diff --check`、最终差异和工作树状态。

L2 在用户指定的真实浏览器、设备或应用环境中走通用户可见流程，保留真实认证、定位、扫码、原生选择器及业务数据条件。UI 复刻对照参考图检查代表性桌面和移动尺寸。记录一种状态：

- `passed`：路径和观察结果。
- `blocked`：阻塞条件及已通过的 L1 证据。
- `user-verified`：用户明确确认界面或流程通过。

需要用户负责视觉或真机验收时，提供已授权启动的服务地址并等待确认。
Craft 来源的状态只按 `craft-issue-tracker/references/workflow.md` 判定：代码修改完成但适用验证尚未完成时记录 `AI 本地已修复`；适用验证全部通过并完成本缺陷提交后记录 `AI 已验证`。验证失败或受阻时保持 `AI 本地已修复`，在本轮日志中写明缺口，不把它解释为用户验收或发版。

## 4. 提交与合入

用户明确不提交时遵从；否则本缺陷所需验证通过后立即原子提交：

1. 重查工作树状态和 `git diff --check`。
2. 只暂存本缺陷文件或精确 hunk，并检查 staged diff。
3. 遵循仓库提交规范；无约定时使用 `fix: <缺陷编号> <简洁行为描述>`。
4. 提交本缺陷的完整改动，报告真实哈希和剩余工作树状态后，再处理下一项或回写 Craft。

验证失败、所需验收受阻或无法隔离无关改动时，先解决阻塞并保留证据。

只有用户明确要求时才合入或推送。操作前检查目标工作树和提交祖先关系，保留无关改动，再选择 fast-forward、merge 或 cherry-pick。

## 5. 纠错回滚

后续证据推翻代码层根因时，停止扩展补丁，确认修改传播到的分支和远端。已共享提交使用可审计的 `git revert`；只向用户明确指定的分支传播反向修改，并逐分支验证代码效果已撤销。

## 6. 交付与完成

交付卡报告根因、行为变化、修改文件、检查结果、L2 状态、基线问题和剩余风险。

完成须同时满足：修复前后证据可区分、定向验证通过、本次差异仅含缺陷改动、L2 状态如实记录、提交/合入/推送符合用户授权；Craft 来源还须完成原条目回写和回读。否则报告 `blocked` 或保持未完成。
