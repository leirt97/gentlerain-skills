# itsaplan 来源回写

## 绑定

itsaplan 来源待办的修复包含原待办回写；用户明确只读、只改代码或不写 itsaplan 时说明未同步。执行前读取 `itsaplan-tracker`，沿用其状态权限、记录格式和接口要点；用户指定状态时记录依据。

按项目 ref、事项 identifier 及 `原编号`（来源系统缺陷编号或 `DYYMMDDNNN`）交叉核验原待办。描述中的图片附件属于来源证据，保持原样。绑定不明时先查上下文，仍不明才询问；可独立推进已授权诊断。

## 处理节点

- 开始处理：用 `itsaplan-tracker` 的 `scripts/list.mjs --number <原编号>` 读状态列，用 `feed?filter=comments&limit=5` 读最新评论，将可开始的待办移到 `AI 处理中`，发一条评论记录本轮原因与开始。用户已推进为 `已发版`、`已关闭` 等状态或交付意图不明时，先核实是否重新修复。
- 修复与验证：本轮修复轮次评论写根因、修改说明、L1/L2 环境、步骤、结果和限制；失败、暂停和环境受阻也须记录。
- L1 与提交完成：代码修改后的相关 L1 通过即完成本待办原子提交，记录真实哈希；在 L2 尚未 `passed` 前按 `itsaplan-tracker/references/workflow.md` 移到 `AI 本地已修复`，评论记录 L2 缺口。
- L2 完成：在已有提交基础上，于真实网页或真机/真实 App 完成 L2，记录路径、观察结果并确认 `passed`，再移到 `AI 已验证`。该状态不代替用户验收或发版。L2 截图存到任务工作目录，不放进项目；需要留证的截图以 `L2-<文件名>` 上传为该待办附件，在评论中按文件名引用，回读附件列表后用 `/usr/bin/trash` 移到废纸篓。
- L1 失败或提交未完成：保持 `AI 处理中`；提交后 L2 失败或受阻：保持 `AI 本地已修复`，评论记录结果、阻塞原因和下一动作。
- 再次代码修复：新开一轮修复轮次评论；撤销时记录原因、反向提交和剩余影响。

## 回读与交付

写前重读，保护用户同期编辑；结果不明先回读已完成部分再继续。用 `list.mjs --number` 核对原待办 identifier 与状态列，用 `feed?filter=comments&limit=1` 核对本轮评论的提交号与验证结论。本流程只追加评论、不改描述和历史评论，所以不回读它们的全文。

代码完成但 itsaplan API 失败时，分别报告代码结果和同步阻塞，恢复后只补未成功部分。最终提供待办链接（`<appUrl>/<team>/issue/<identifier>`，如 `/dahehu/issue/RHL-53`）、当前状态、轮次与提交、回读结果和验收缺口。
