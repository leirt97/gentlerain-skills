# Craft 来源缺陷回写

## 绑定

Craft 来源缺陷的修复包含原问题回写；用户明确只读、只改代码或不写 Craft 时说明未同步。执行前读取 `craft-issue-tracker`，沿用其状态权限、日志格式和 API 规则；用户指定状态时记录依据。

按源文档、合集、条目 ID 及已解析编号（来源系统缺陷编号或 Craft 问题编号）交叉核验原条目。原始问题中的图片或其他媒体块属于来源证据，沿用其字段归属、顺序和 Craft block ID。绑定不明时先查上下文，仍不明才询问；可独立推进已授权诊断。

## 处理节点

- 开始处理：重读状态和最新反馈，将可开始的待办更新为 AI 处理中，记录本轮原因与开始事件。用户已推进为已发版、已关闭等状态或交付意图不明时，先核实是否重新修复。
- 修复与验证：向本轮补充根因、修改说明、L1/L2 环境、步骤、结果和限制；失败、暂停和环境受阻也须记录。
- L1 与提交完成：代码修改后的相关 L1 通过即完成本缺陷原子提交，记录真实哈希；在 L2 尚未 `passed` 前按 `craft-issue-tracker/references/workflow.md` 记为 AI 本地已修复，并记录 L2 缺口。
- L2 完成：在已有提交基础上，于真实网页或真机/真实 App 完成 L2，记录路径、观察结果并确认 `passed`，再将状态记为 AI 已验证。该状态不代替用户验收或发版。
- L1 失败或提交未完成：保持 AI 处理中；提交后 L2 失败或受阻：保持 AI 本地已修复，记录对应结果、阻塞原因和下一动作；再次修改代码时新开修复轮次。
- 再次代码修复：按 `craft-issue-tracker` 新开轮次，同轮验证反馈按其格式追加并保留历史；撤销时记录原因、反向提交和剩余影响。

## 回读与交付

写前重读，保护用户同期编辑；结果不明先回读已完成部分再继续。核对原条目 ID、状态、本轮日志、提交号、验证结论、媒体字段归属、媒体块顺序与 ID 及旧轮次完整。

代码完成但 Craft API 失败时，分别报告代码结果和同步阻塞，恢复后只补未成功部分。最终提供问题链接、当前状态、轮次与提交、回读结果和验收缺口。
