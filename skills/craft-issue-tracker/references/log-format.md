# 日志格式

问题详情顺序：修改日志、原始问题与实际结果、复现步骤、预期结果、原文链接。

日志位于顶部，事件按时间倒序，使用同级三级标题。标题不放时间；标题、正文和末尾时间分别用独立 Craft 块，时间作为独立块以行内代码表示。只记录真实发生的创建、迁移、修复等事件；各事件保持独立，不把创建或迁移说明并入修复轮次。

## 修复轮次

每轮正文使用短字段分行，按实际内容填写：

```text
根因：<有证据支持的直接原因>
修复：<本轮改动及结果>
验证：<环境、核验方式和实际结果>
提交：<真实提交哈希>
待验证：<尚缺的验证及所需证据>
```

只显示有事实内容的字段。`根因`仅在证据支持时说明导致现象的直接原因；未知或不适用时省略，不以症状复述代替根因。`修复`写清本轮改动。`验证`用简短结果概括环境、关键操作或测试；只有预期与实际不一致或需要消除歧义时才分别说明。测试写命令或范围及结果摘要，附件只保留可定位的引用，不复述附件内容。提交字段只列实际提交；多笔原子提交可并列记录。

不重复原问题、复现步骤、已说明的预期结果或前轮背景。失败时保留发生环境、实际现象及下一步；受阻时写明阻塞点和恢复所需证据。按 [流程与权限](workflow.md) 记录状态所必需的信息，特别是 `AI 本地已修复` 所需的 L1 结果、提交哈希及 L2 缺口。

已收到的用户反馈才记录，并附反馈时间；同轮多次反馈按时间倒序追加，不覆盖历史。再次修改代码时新开一轮。

## 原始问题与实际结果

来源原文原样保留在 `问题描述`。外部系统的导入与刷新按其同步契约写入，不自动增补；AI 自拟的问题或用户要求整理时，在其前后增补以下各项，用加粗字段名分段，让读者不读代码也能看懂：

- `一句话说明` 放在最前：用户看到的现象、有证据的直接原因和影响范围；原因未核实时只写现象。
- `数据流` 在涉及 3 个以上组件、调用链或数据流时加：代码块中的文本树，只用缩进和 `├─`、`└─`（不画右边框，中文对不齐），断点用 `✗` 标出。
- `实际结果` 一条写一个事实并附依据 `文件:行号`，未核实的写“推断”；并列多个对象类型时，用 `范围说明` 写明哪些真受影响、哪些仅预留。
- `核对版本` 写仓库与提交及核对方式（静态或运行时）；`名词说明` 只列首次出现且读者可能不熟的术语和“端”的叫法，沿用项目通用叫法，一条一句。
- 增补记为独立的“整理详情”日志事件，写明新增内容及来源。

## 时间

时间格式为 `YYYY-MM-DD 星期X 上午/下午h:mm`，使用上下文确认的时区，默认 `Asia/Taipei`。原始记录保留其时间精度；缺少时分时注明“原记录未记具体时分”。
